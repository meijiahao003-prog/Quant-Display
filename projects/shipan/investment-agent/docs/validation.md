# v0.1 验证记录

## 2026-10-19 修复记录

用户截图已显示服务就绪、ChatGPT 账户已登录，但真实连接验证返回 `askForApproval.granular requires experimentalApi capability`。问题出在本项目协议配置：`generate()` 使用 granular 策略，初始化却设置了 `experimentalApi: false`。

本次将初始化改为 `experimentalApi: true`。只读沙箱、工具禁用与 granular 的五个拒绝项均保留。根据 [官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)，该开关用于允许受门控的协议方法及字段，不表示授予工具执行批准。

此前“45 项测试通过”只涵盖当时列出的测试用例，并未覆盖真实生成参数的能力门槛；旧的协议探针用了简化的 `approvalPolicy: 'never'`，与实际生成路径不一致，所以漏掉了这次错误。本次新增 `npm run verify:capabilities`，直接取得生产 `generate()` 构造的参数，再交给真实 Codex 校验。原始结果见 [能力门槛回归记录](capability-regression.json)。

该回归检查不会登录用户账户或进行模型推理。修复后账号下的真实回答与完整会话恢复，仍须用户重启平台后点击验证按钮确认。截图能证明已登录，不能证明模型生成已成功。

本次实际结果：原有 45 项测试全部通过；新增真实 Codex 协议探针 6/6 符合预期。关闭 capability 时三个方法均复现原报错；打开后 `thread/start` 成功，`thread/resume` 与 `turn/start` 通过字段门槛并按设计拒绝不存在的线程。这两个拒绝结果用于证明未触发推理，不代表已完成真实会话恢复或模型回答。

以下保留初版验证范围；自动测试输出在本次修复后重新生成。

验证日期：2026-10-18。环境：Linux、Node.js v24.19.0、npm 11.9.0、官方 `@openai/codex` 0.163.0。

## 测试涵盖的主要行为

- 首轮三个角色的提示与线程独立；后续轮次才引入其他人的意见。
- 每轮三位专家加主持人，最多 3 轮、12 次请求；自报高置信度不能覆盖证据缺口。
- 主持人不能覆盖立场冲突或明确登记的异议；不存在的材料编号、未提供材料及缺失证据阻止成功结论。
- 失败、非法 JSON、取消与异常中断保存已完成成果，不伪造最终答案。
- 仅当模型的终结事件为成功且包含有效答案时接受结果；片段文本不能掩盖终结失败。
- 登录与验证分别判断；验证必须有两次精确响应，并在进程重启后恢复原线程。
- 换模型后需要重新验证；验证失败、未登录及未验证状态不能发起研究。
- 同时提交的研究、验证和登录互斥，阻止重复消耗额度。
- HTTP 的 Host、Origin、跨站请求、CSRF 与输入限制；凭据环境隔离和错误脱敏。
- 进程关闭与重启的生命周期；异步页面回调失败不会被当作成功回答。

## 仍需在用户电脑完成

1. **ChatGPT 登录与授权**：点击连接设置，在官方页面完成；设备码是否开放取决于账号设置和工作区策略。
2. **真实模型生成与恢复**：选模型后点击验证，平台依次完成第一轮回答、进程重启、`thread/resume`、第二轮校验。会消耗两次实际模型请求。
3. **真实专家会审**：提供自己的材料进行一次研究，确认模型能稳定返回要求的 JSON，并逐条检查引用与结论。
4. **质量评估**：本版没有用历史投资案例评估正确性、回测表现或专业专家一致性，也没有训练投资专家模型权重。
5. **Windows / macOS**：已提供启动脚本，尚未在这两类操作系统实跑。Windows PowerShell 脚本仅做代码检查，没有伪称已运行。

平台仅按提供材料进行文本研究，没有自动接入金融行情、联网核验、ClickHouse、QMT 或下单功能。编号可追溯不代表事实已核实；同一模型的多个角色也不构成独立信息源。
